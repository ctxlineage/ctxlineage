# M4 — MCP Server (`ctxlineage-mcp`)

> **For Claude:** TDD, one PR ("part of #4"). PLAN.md §4(c): stdio MCP server with
> read-only tools `list_sessions` / `get_call` / `get_lineage` / `generate_report`,
> so coding agents can read the context breakdown and lineage without opening the
> HTML report. §6: the MCP server is the third layer over the same JSONL. §7: the
> official `mcp` Python SDK (FastMCP).

**Goal:** a coding agent connected via stdio can answer "what did the latest call
consume, where did it flow, and give me the report" — using exactly the same
numbers the HTML report shows.

## Hard constraints

- **Single source of truth:** all data comes from
  `ctxlineage._report.normalize.load_events()` + `build_report_data()`. No
  re-implementation of segment matching, edge inference, or element assembly.
  The MCP layer only *selects and summarizes* from the report-data contract
  (`sessions[].calls / edges / elements`, `stats`).
- **Do not touch** `src/ctxlineage/_instrument/` (PR #31 in flight) or
  `src/ctxlineage/_report/` + assets (PR #32 in flight). `ctxlineage_mcp` only
  *imports* the current main contract; #32's additive fields (e.g. per-element
  `tokens_est`) pass through untouched once merged.
- Read-only over the event log: no tool ever writes to `.ctxlineage/`.
  `generate_report` writes the HTML artifact (same behavior as the CLI), which
  is the sanctioned exception.

## Package & packaging

```

└── server.py          # FastMCP app, 4 tools, click entry point
```

  - `[project.optional-dependencies] mcp = ["mcp>=1.2"]` — keeping the base
    install minimal is an explicit design goal (CLAUDE.md); the server is an
    opt-in integration (`pip install ctxlineage[mcp]`). `mcp` is added to the
    dev group so tests always run.
  - `[project.scripts] ctxlineage-mcp = "ctxlineage_mcp.server:main"`.
  - `tool.hatch.build.targets.wheel.packages += src/ctxlineage_mcp`.
- Importing `mcp` lazily-guarded: a missing extra produces an actionable error
  ("pip install 'ctxlineage[mcp]'"), not a bare ImportError traceback.

## Server design

- `FastMCP("ctxlineage")`, stdio transport (`mcp.run()`), CLI: `ctxlineage-mcp
  [--dir .ctxlineage]` (click, same option/default as `ctxlineage report`).
- Events are re-read per tool call through a tiny `(mtime_ns, size)` cache —
  the JSONL is append-only and may grow while the server runs; a stale server
  would defeat the "analyze the latest call" use case.
- IDs: calls already carry `call_id`. Elements get a synthetic
  `element_id = "{span_id}:{name}"`, included in every element payload so
  agents can feed it back to `get_lineage`.
- Errors return actionable messages (e.g. missing events file → "run your app
  with ctxlineage.init() first (or pass --dir)"; unknown id → suggest
  `list_sessions`). Raised as `ValueError`/`FileNotFoundError`; FastMCP converts
  them into tool errors.

## Tools (all return dicts → structured content)

1. **`list_sessions()`** — global `stats` (incl. tag match rate) + one summary
   per session: `id, started_at, ended_at, call_count, error_count, models,
   call_ids, element_ids`. No prompt bodies — this is the cheap index tool.
2. **`get_call(call_id, full_content=False)`** — the normalized call dict plus
   `session_id`. By default each segment `content` and the output are truncated
   to 700 chars with `content_truncated: true` (context hygiene for agents);
   `full_content=True` returns everything verbatim.
3. **`get_lineage(id)`** — accepts a `call_id`, an `element_id`
   (`span_id:name`), or a bare element name if unambiguous.
   - call: `{node, elements_consumed, edges_in, edges_out,
     downstream_call_ids}` (transitive closure over the session's edges —
     PLAN's "primitive impact analysis").
   - element: `{node, consuming_call_ids, downstream_call_ids}` (closure from
     the consuming calls).
   - Includes `edges_truncated` passthrough so agents know when inference was
     capped.
4. **`generate_report(out="ctxlineage-report.html")`** — same pipeline as the
   CLI (`build_report_data` → `html.render`), returns
   `{path (absolute), sessions, calls, skipped_lines}`.

## Tests (`tests/test_mcp_server.py`)

Fixtures write a small `events.jsonl` (reusing shapes from `test_normalize.py`:
2 sessions, tags, an output→input flow, an error call).

1. Tool registration: the FastMCP instance exposes exactly the 4 tools
   (`await mcp.list_tools()`), server name `ctxlineage`.
2. `list_sessions`: session count/order, summary fields, no segment bodies.
3. `get_call`: found (segments + usage intact; truncation flag on long content;
   `full_content=True` roundtrip) / unknown id → actionable error.
4. `get_lineage`: by call_id (edges in/out, transitive downstream), by
   element_id, by unique bare name, ambiguous name → error listing candidates.
5. `generate_report`: HTML written to tmp_path, contains embedded data.
6. Freshness: append an event to the JSONL after a first call → next
   `list_sessions` reflects it (cache invalidation).
7. Missing events file → actionable error naming the dir and init().

Integration is tested against the FastMCP instance in-process
(`mcp.call_tool(...)`) — no subprocess/stdio harness needed; stdio is SDK
plumbing, not our code.
