# Redaction: `report --redact` + capture-side field masking

> **For Claude:** TDD, one PR. Part of #4 (v0.1.0). Spec anchor: PLAN.md §6
> "Sensitive data" — *"Provide at minimum `ctxlineage report --redact
> "pattern"` and field-level masking via init options."* SECURITY.md and
> README already promise this for v0.1.0.

**Goal:** let users share reports (and event logs) without leaking secrets,
without compromising the honest-data principle: redaction happens *after*
segment matching and edge inference, is always disclosed, and never fabricates.

## Two independent layers

### 1. Report-side pattern redaction (share-time)

```
ctxlineage report --redact "sk-[A-Za-z0-9]+" --redact "alice@example\.com"
```

- `--redact PATTERN` — repeatable Python regex. Invalid regex →
  `click.ClickException` naming the bad pattern.
- Applied by `_report/redact.py: apply(data, patterns) -> count` to the
  normalized report data (deep, in-place on the built dict), *after*
  `build_report_data` — so token estimates, match rate, and lineage edges are
  computed on the real text and stay honest.
- Every regex match is replaced with `[redacted]`.
- Fields walked (the free-text carriers; ids/models/timestamps/kinds are
  structural and untouched):
  - `sessions[].calls[].segments[].content` (includes `tool_defs` JSON)
  - `sessions[].calls[].segments[].source` / `.transform` (tag provenance)
  - `sessions[].calls[].output.content`
  - `sessions[].calls[].error.message`
  - `sessions[].elements[].source` / `.transform`
- Disclosure: `data["redaction"] = {"patterns": <n>, "matches": <m>}` (never
  the patterns themselves — they may contain the secret). Overview shows a
  one-line notice when present. `--json` output carries the same key.
- Works with `--json`, HTML, and `--open` identically.

### 2. Capture-side field masking (write-time, init option)

```python
ctxlineage.init(redact_fields=["request.messages", "response"])
```

- `redact_fields: list[str]` — dotted paths into the event `payload`. At
  emit time each resolved value is replaced with the string `"[redacted]"`
  before the event is written to `events.jsonl` (the secret never touches
  disk).
- Path semantics: split on `.`; dict keys traverse; when a path segment
  lands on a list, the rest of the path applies to every item
  (`request.messages.content` masks every message's content). Missing paths
  are a silent no-op.
- Applies to every event type's payload (llm_call, tag — so
  `redact_fields=["content"]` masks tag bodies too).
- Never breaks the host app: masking runs inside `emit`'s existing
  try/except; a failure degrades to writing the *unmasked* event is NOT
  acceptable — on masking failure the event is dropped with a
  `warn_once`, because silently leaking what the user asked to hide is the
  worse failure.
- Trade-off stated in docs: capture-side masking is irreversible and blinds
  segment matching for the masked fields (matching then sees
  `[redacted]`). Prefer report-side `--redact` unless the log itself must
  stay clean.

## Out of scope (follow-ups)

- `generate_report` MCP tool gaining a `redact` parameter (needs the same
  plumbing; file an issue after this lands).
- Named entity / automatic PII detection — never (guessing violates honest
  data).

## Tests (tests/test_redact.py + test_init additions)

- report-side: matches masked in segment content / output / tool_defs /
  error message / element+segment source+transform; token counts and match
  rate unchanged; ids/models untouched; multiple patterns; zero matches →
  no `redaction` key change (`matches: 0`); invalid regex → ClickException;
  CLI HTML output contains no matched text; `--json` carries `redaction`.
- capture-side: masked field is `"[redacted]"` in the JSONL; list traversal;
  missing path no-op; tag payload masking; masking failure → event dropped +
  warning, host call unaffected.
